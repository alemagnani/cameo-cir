# CAMEO-CIR — Progress Summary (2026-06-07)

## 0. TL;DR
- **Task:** Composed Image Retrieval over 4,075 face-cleanser products (NTCIR-19 CAMEO). Given a reference product image + a natural-language modification, return a ranked list.
- **Pipeline:** Stage-1 retrieval (CLIP-family) → Stage-2 listwise rerank (VLM).
- **Biggest win so far:** a **local open-weights VLM reranker beats the Claude-Haiku API reranker at ~$0 marginal cost** (Qwen2.5-VL-72B **0.913** vs Haiku 0.872 on official-20, judge NDCG@10).
- **Biggest realization:** on our exact-match dev set, **Stage-1 recall is the true bottleneck**, not the reranker. open_clip **ViT-H quadruples recall** vs the old SEARLE/Phi stage-1 (R@20 0.343 vs 0.084). Fixing Stage-1 is the current focus (GPU run in flight).

---

## 1. Data: ours vs. organizer-provided

| | **Organizer-provided** | **Ours (synthetic dev)** |
|---|---|---|
| Corpus | 4,075 products (shared) | same 4,075 |
| Queries | **20 official CIR queries** (real human modification requests) | **429 templated-rule** + ~1,650 LLM free-form (rule5/5a/5b); 2,083 merged |
| Ground truth | **none shipped** → we score with a Claude **judge** (graded relevance) | **exact `answer_product_id`** per query (deterministic) |
| Relevance type | graded / dense (many products count as relevant) | exact / sparse (usually 1 right product) |
| Origin | organizers (natural) | generated by us (templates + Sonnet) |
| Purpose | realistic proxy for the competition metric | cheap, fast, free iteration |

**Key consequences of the difference:**
- **Exact-match (dev-429) is harsh and low-ceiling**: "is *the one* product in top-K." Great for measuring *recall/retrieval*, but absolute NDCG looks tiny.
- **Judge (official-20) is lenient/dense**: many products judged relevant, so scores look high (0.87–0.91). Better proxy for the real competition NDCG/MAP, but small n=20 and judge-dependent.
- **Self-generation bias risk**: our dev relevance reflects our generator's assumptions; treat dev as a *relative* signal, validate direction on official-20.

**Are we only using validation? Yes.** Everything to date is dev/validation:
- dev-429 + LLM dev = our internal validation (we made the labels).
- official-20 = organizer queries, but scored with *our* judge (we don't have the organizers' gold judgments).
- The real **test** = organizers' held-out TREC-style human judgments at submission time — **not available to us**, no leakage. Final numbers come from them.

**Recall sweep conclusion (2026-06-07):** ViT-bigG ≈ ViT-H at the top (~0.43 R@50);
name-fusion adds a marginal bump. **Scaling the visual backbone plateaus** — the exact

**hybrid visual + brand/name-text retrieval** (visual CLIP structurally can't do
`brand_swap` — find a *different* brand — which sits at ~0.04 for every backbone),
not from a bigger visual model.

---

## 3. What worked
1. **Local VLM rerank ≥ Haiku, at ~$0 marginal cost.** Qwen-72B/InternVL3/Qwen-32B all beat Haiku on official-20. This changes the cost structure (see §6).
2. **Better Stage-1 backbones dramatically raise recall** (ViT-H 4× over Phi; OTI 2×).
3. **Diagnosis nailed down:** rerank quality is capped by Stage-1 recall — on dev-429 the answer was in Phi's top-20 only 8% of the time.
4. **EXP-004 OTI** (GPU inversion) confirmed as a real Stage-1 improvement over Phi.
5. **Cheap, free, deterministic dev harness** (exact-match by rule) for fast iteration; judge eval reused from cache → many evals at $0.

## 4. What didn't
1. **Rewritten captions** (block 7) — hurt retrieval & rerank.
2. **Brand fusion** — helps one rule, hurts overall.
3. **GLM-4.5V** — failed to load under vLLM (integration issue).
4. **Pixtral-Large (FP8)** — only model below Haiku.
5. **Ops mistakes (fixed):** torch/driver CUDA mismatch wasted a box; bundling 100B-model downloads under a 3h reaper deadline cut the retrieval passes short; over-provisioned disk inflated cost.

---

## 5. Evaluation going forward (two-track)
- **Track A — dev-429 exact-match (free, deterministic):** use for **retrieval/recall iteration** (R@K, candidate-pool quality). Read as *relative*, not absolute.
- **Track B — official-20 judge (graded):** use for **final pipeline quality**, the closest proxy to the competition NDCG@10 / MAP. Reuse judge cache to keep cost ~$0.
- **Rule:** improve recall on Track A, confirm gains hold on Track B before adopting.
- **Submission:** organizers score the held-out test; we produce `sample_submission.json`-format runs from the final pipeline.

---

## 6. Cost structure (why the GPU work matters)
- **Haiku rerank:** per-token, ~**$11 per full dev rerank**, paid *every* experiment → ~$230 spent historically; rate-limited.
- **Local VLM rerank:** flat **GPU-hour**; once the box is up, the Nth rerank ≈ free; no rate limits.
- A single Haiku dev-rerank ≈ the cost of an entire focused GPU session. Validating the swap pays for itself immediately.
- GPU spend so far (validation): ~$19.5 total (inflated by over-provisioned disk + billed download/setup time — both corrected in the focused run).

### Approach #1: LLM/metadata structured retrieval (2026-06-08/09) — a real new lever
Exploit unused corpus metadata (brand, numeric **price** VND, description). metadata_retrieve.py:
per-query target fields (gold or Haiku-extracted) -> brand match + price proximity + format/claim
keyword scoring. Extraction accuracy (Haiku vs gold dev): brand 100%, format/claim 100% present,
price 100% when stated. **Metadata-priority fusion with bigG (Stage-1, no rerank):**
| dev-429 Stage-1 | NDCG@10 | R@50 |
|---|---|---|
| bigG (visual) | 0.157 | 0.436 |
| metadata-fused (extracted) | **0.200** | **0.527** |
Per-rule (extracted-fused): cheaper 0.293, pricier 0.362, format 0.234, brand 0.117, claim 0.173 —
the **price** signal (never used before) nails cheaper/pricier; R@50 up to 0.60+ on structured rules.
Full-dev 2,083: fused 0.115 ~= bigG 0.119 (neutral on the 79% free-form, big win on templated).
**Reranking the fused pool HURTS on exact-match dev (0.200->0.173)** — metadata (brand/price/format
exact match) is **orthogonal** to what the visual VLM optimizes, so rerank demotes structural matches.
**But on official-20 judge: metadata-fused + Qwen-72B = NDCG@10 0.923** — best official yet (vs 0.913/0.883),
n=20 + MAP-bug caveats. Takeaway: metadata is the best lever for *structured* queries; don't visual-rerank it.
